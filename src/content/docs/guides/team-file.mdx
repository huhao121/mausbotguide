A bot that can do everything is slow at everything. Use a few bots instead, each with a narrow
job and only the tools that job needs.

<Figure name="team-file" alt="A three-panel geometric poster: three identical robots, each with one tool only: a speech bubble, a mouse connected to a monitor, and a flashlight under a clock." />

## Before you start

- An OpenMausBot server you can reach with `ssh myserver` from this computer (see [how to run OpenMausBot 24/7 on a home server](/guides/home-server/)).
- At least one engine signed in (see [how to sign in to engines](/guides/sign-in-engines/)).

Below, `myserver` is the server's SSH alias and anything in `<…>` is a value you replace.

## Decisions

| Bot | Model | Tools | Use it for |
|---|---|---|---|
| **Chat** | Fast and cheap, low effort | Shell and files only, **no computer** | Questions, writing, summaries. Replies in seconds. |
| **Operator** | Strong | Browser + a computer (local VM) | Clicking through websites, screenshots, anything visual |
| **Patrol** | Cheapest | Whatever the routine needs | Scheduled checks that report only when something changed |

Why split: every tool a bot has is described in every prompt, and a bot with many tools has more ways to take a long
detour. Keeping each bot to the tools its job needs keeps tasks short. See
[why one task can take an hour](/concepts/long-tasks/).

## Hand this to your agent

OpenMausBot can be set up from a team file, so your agent can create bots without clicking through dialogs.

```text title="Prompt"
On my OpenMausBot server (ssh alias "myserver"), set up three bots with `openmausbot team export` / `team apply`:

- "Chat": model <fast model>, effort: low, computer: off, approval: ask.
- "Operator": model <strong model>, computer: vm, approval: ask.
- "Patrol": model <cheapest model>, computer: browser, approval: full (it runs unattended, so nobody is there to answer a card).

First export the current team to a file and show me the diff before applying (team apply --check).
Then create a routine for Patrol: every weekday at 09:00 my time, check <what to check> and post a short summary only
if something changed. Finally prove each bot works with `openmausbot run "<bot>" "<small task>"` and show me
the replies.
```

## What a team file looks like

<Diagram name="team-file" alt="A team.yaml has three parts: defaults that every bot uses unless it sets its own, bots with one entry each covering model, approval, computer and standing instructions, and rooms with members and a shared brief." />

A team file describes the whole workspace: bots, their models, approval levels and computers, their standing
instructions, rooms, and the engines they use. A complete, realistic example:

```yaml title="team.yaml"
version: 1

defaults:                     # every bot gets these unless it sets its own
  approval: full              # nobody is there to answer a card
  computer: off
  cwd: /home/bot/work

teams:
  - name: Content
    brief: |
      Data, copy and visuals are separate jobs; when handing work on,
      always write where the results and files are.

bots:                         # at least one
  - name: Chat
    team: Content
    model: claude/claude-sonnet-5         # INSTANCE/MODEL, exactly as `openmausbot models` prints it
    effort: low                           # none | low | medium | high | xhigh | max
    approval: full
    computer: off
    soul: |                               # standing instructions: sent with every turn
      You handle everyday questions and writing. Answer briefly, conclusion first.

  - name: Patrol
    team: Content
    model: opencodeGo/opencode-go/deepseek-v4.1-flash
    approval: full
    computer: browser
    cwd: /home/bot/work/patrol          # a full path on the server; ~ is refused
    skills:
      - { file: skills/report/SKILL.md, enabled: true }   # path relative to this file
    soul: |
      You run the scheduled checks. Report only when something changed;
      when nothing did, reply with one line.

  - name: Operator
    team: Content
    chief: true                           # one Chief per team
    model: antigravity/gemini-3.8-flash
    approval: ask                         # this one touches production
    computer: vm
    cwd: /home/bot/work/ops
    browser: { enabled: true, profile: guest }
    soul: |
      You do the jobs that need a screen. Ask before touching production, and say in the
      approval request what you are about to run.

rooms:
  - name: Weekly
    team: Content
    members: [Chat, Patrol, Operator]     # bot names
    brief: Every Monday, put last week's numbers and next week's topics here.
    responder: mentions                   # everyone | mentions | a bot name
```

A few fields the example doesn't explain:

| Field | Why it matters |
|---|---|
| `engines:` | Optional, and needs full access. Keys must be `{ env: NAME }` or `{ file: PATH }`; a key written into the file is refused |
| `defaults:` | Applies to every bot that doesn't set the field itself |
| `approval:` | A new bot starts at `full`. Unattended bots need it; see [approval levels](/concepts/approval-levels/) |
| `cwd:` | Must be a full path that exists on the server; `~` is refused because it may mean something else there |
| `soul:` | Standing instructions, at most 24,000 bytes; `{ file: PATH }` keeps them in a file instead |
| `tools:` | `{ allow: [...] }` or `{ deny: [...] }` narrows what the bot can use; leave it out and it gets everything |
| `prune: true` (on a team) | Only a team marked this way lets `--prune` delete bots and rooms the file no longer lists |

When you apply a team file:

- You can preview the changes first without applying them.
- Bots are matched by name. To rename one, use `was:` with its old name. Fields the file leaves out stay as they are.
- If a step is refused, it stops and tells you what it already did. Applying again carries on.
- It does not delete bots or rooms by default. Only teams marked `prune: true` can have them removed when you apply.

## Let other agents give bots work

You don't have to open the app to give a bot work. Claude Code, Codex and OpenCode can hand jobs to your bots and wait for the results. Send this to your AI agent:

```text title="Prompt"
Connect my OpenMausBot server (ssh alias "myserver") as an MCP server using `openmausbot mcp`, and add it to your own MCP config.
Then have "<bot name>" do one small job: <task>. Wait for it to finish and show me the result.
```

## Habits that keep it fast and safe

- One job, one conversation. Start a new conversation per task.
- Set approvals deliberately. Every new bot, from the app or a team file, starts at `full` (Full access), so
  write `approval:` for each bot. Bots that run routines need `full`, or they wait on a card nobody answers. Use `ask`
  for bots whose actions you want to check. `edits` exists only on engines that offer it (Claude, Antigravity, Grok),
  not on OpenCode or Codex. On a Mac home, bots run as you, so be stricter there.
- **Connected apps are greyed out on a self-hosted server** until you add a **Composio project key** (Settings → API
  keys → Self-host connected apps). Before that, a CLI is often simpler: install `gh` on the server and sign in with a device code, and bots
  can use GitHub immediately. Note that a self-hosted Composio key can call app tools but cannot watch for app events
  yet. Use webhooks for "when X happens".
