有一次，我们让一个 Bot 做一项分析任务，它跑了整整 **60 分钟**，用量记录里这一轮的输入是 **1104 万 token**。

我们第一反应是"上下文太大，模型变慢了"。可拆开这一轮的逐步记录一看，并不是。

## 这 60 分钟花在了哪

这一轮跑在 Gemini 3.8 Flash 上：

| 项目 | 数值 |
|---|---|
| 总耗时 | 60 分钟 |
| 模型调用 | 约 90 次，累计约 32 分钟 |
| 工具执行 | 178 次，累计约 39 分钟（两者在时间上有重叠，所以相加超过 60 分钟） |
| 工具构成 | 60 次在虚拟机里执行命令，35 次运行 Python 脚本，操作屏幕的只有 15 次 |
| 上下文大小 | 从 2.9 万 token 涨到 35.5 万 token |
| 累计输入 | 1104 万 token，其中 1069 万（97%）命中缓存 |
| 估算费用 | 约 1.18 美元 |

所以：

- 慢，是因为步骤多。每一步都要等模型想好下一步，再等工具执行完。上百步加起来就是一个小时。
- 1104 万不是上下文大小。上下文最大只有 35.5 万。1104 万是约 90 次调用的输入加在一起。

## Mac 上也一样

我们自己的 Mac 上，Claude Opus 5.5 有一轮用了 16 分钟、64 次模型调用、64 次工具执行：

| 项目 | 这台 Mac 上的一轮 |
|---|---|
| 总耗时 | 16 分钟 |
| 模型调用 | 64 次，累计约 6 分钟（中位数 3.9 秒） |
| 工具执行 | 64 次，累计约 9 分钟（中位数 0.5 秒） |
| 上下文大小 | 从 4.1 万 token 涨到 15.3 万 token |
| 累计输入 | 594 万 token，其中 97% 命中缓存 |
| 费用 | 约 3 美元，由模型服务方直接报数，不是估算 |

换了机器、模型和服务商，结果还是一样：**慢的不是单次调用，是一轮里次数太多。** 这台 Mac 上单次调用的中位数只有 3.9 秒，一轮却有 64 次调用和 64 次工具执行。时间就是这么一步步攒出来的。工具甚至比模型还费时间，有几次执行就接近两分钟。

## token 为什么会累计到上千万

同一轮里，每次调用模型都要把**到目前为止的整个对话**再发一遍。

下图是这一轮里每次模型调用实际发送的上下文大小（来自用量记录）：

<Diagram name="context-growth" alt="柱状图：同一轮里 88 次模型调用，每次发送的上下文从第 1 次的 2.9 万 token 增长到第 88 次的 35.5 万 token。" />

上下文每步都在变长，每步又都要重发一遍，累计输入就会远大于最终的上下文。好在重复的部分大多命中缓存：这一轮 97% 的输入是缓存命中，缓存部分比正常输入便宜得多，所以总共只花了约 1.18 美元（按 API 价格估算）。

## 上下文变大会让每次调用变慢吗

在我们的数据里，不明显。下面是我们服务器上两天内所有模型调用按上下文大小分组的**单次耗时中位数**（单次耗时包括读入上下文和写出回复）：

| 上下文大小 | DeepSeek V4.1 Flash（OpenCode Go） | Gemini 3.8 Flash |
|---|---|---|
| 5 万以下 | 4.9 秒（22 次） | 15.0 秒（27 次） |
| 5–10 万 | 14.3 秒（23 次） | 8.9 秒（143 次） |
| 10–20 万 | 13.4 秒（45 次） | 7.3 秒（243 次） |
| 20–30 万 | 16.7 秒（16 次） | 8.0 秒（170 次） |
| 30–40 万 | 12.4 秒（16 次） | 9.7 秒（59 次） |

单次调用一般在 5 到 17 秒之间，没有随上下文变大而成倍变慢。最慢的几次调用在 1 到 2.5 分钟之间，分散在各个上下文区间，并没有集中在大上下文上。

## 怎么让任务更快、更省

| 做法 | 为什么管用 |
|---|---|
| **一件事开一个会话** | 新会话从小上下文开始，每步重发的内容少，累计 token 也少 |
| **把大任务拆成几个小任务** | 步骤少了，等待就少了；中途出错也不用从头再来 |
| **让 Bot 把重复的活写成脚本** | 我们的 GSC 日报每天运行一次只要 19 步、不到 3 分钟，因为重活都在脚本里 |
| **不需要看屏幕的 Bot 不给电脑** | 可用的工具越少，Bot 绕远路的机会越少 |
| **日常聊天用低思考强度** | 思考 token 少了，每一步更快 |
