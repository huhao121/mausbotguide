一个 Bot 什么都干，最容易出两种问题：它的指令越写越长，它的权限越来越大。把活拆成三个岗位，每个岗位只做一件事，有自己的指令和目录，出错时也知道该找谁。目录决定它在哪工作，不是权限边界。

这一页带你搭一支三人小队：一个总协调机器人接活，一个研究员给要点，一个编辑成稿。目标是拿到一份编辑写出的 `roles.md`，还有一条能逐行读的接力记录。

开始前需要三样东西：能真正跑起来的 OpenMausBot（这一页在 0.1.154 上验证）、至少一个已经配置好并且能运行的引擎、三个给 Bot 当工作目录的文件夹。下面用 `<team file>` 表示这份 YAML 文件，用 `<shared folder>` 表示三个 Bot 都能写的那个目录，用 `<output folder>` 表示放运行结果的空文件夹。

## 一份活怎么走完

<Diagram name="three-bot-handoff" alt="接力顺序：你向总协调机器人提一个需求，它把要点任务派给研究员，研究员交回要点表，它再把要点表和文件路径交给编辑，编辑写入 roles.md，它读一遍文件确认后才回复你。" />

顺利的话，你只对总协调说话。它先拆需求，把“列要点”交给研究员，拿到要点表后再把“写成文件”交给编辑。编辑写完，它自己读一遍文件，确认路径和内容都在，才回你几行。

研究员的活和编辑的活是串行的。要点表没出来之前，编辑不该动笔，否则它没有可写的依据。

## 三个角色怎么分

| 角色 | 负责 | 不负责 | 交接物 |
|---|---|---|---|
| 总协调 | 拆解需求、派活、验收、汇总 | 查事实、写长文 | 给专才的 brief，给你的短汇报 |
| 研究员 | 列要点、给依据、标可信度 | 写成品、润色 | 带依据的要点表 |
| 编辑 | 按要点表成稿、写入文件 | 补事实、改结论 | 指定路径的文件，加一行依据 |

写指令时只写三件事：它负责什么，它不负责什么，它交出什么。第三件最重要，格式写死了，下一棒才接得住。

研究员的交付物可以固定成三列：要点、依据、可信度。编辑的交付物固定成两样：文件路径和字数。总协调的汇报固定成六行以内。三五行就够，不用写成长篇教程。

## 搭起来

先让总协调接活，研究员和编辑各管一段。三个岗位写在同一份 team 文件里：

```yaml title="team.yaml"
version: 1
defaults:
  approval: full   # 无人值守，没人接审批卡
  computer: off
  browser: false
teams:
  - name: Demo Lab
    brief: |
      三个岗位：总协调接活与验收，研究员给要点，编辑成稿。
      小队约定：所有产出只写到 <shared folder>，不对外发送，不安装软件。
bots:
  - name: Alder
    team: Demo Lab
    chief: true
    title: Chief of Staff
    model: <INSTANCE>/<MODEL>
    cwd: <shared folder>
    soul: { file: souls/alder.md }
  - name: Sorrel
    team: Demo Lab
    title: Researcher
    model: <INSTANCE>/<MODEL>
    cwd: <research folder>
    soul: { file: souls/sorrel.md }
  - name: Larch
    team: Demo Lab
    title: Editor
    model: <INSTANCE>/<MODEL>
    cwd: <edit folder>
    soul: { file: souls/larch.md }
```

示例用 Alder、Sorrel、Larch 和 Demo Lab；换成你自己的名字。下面用「总协调 / 研究员 / 编辑」指代这三个岗位。

在一次演示运行里，编辑写出了 `roles.md`。下面的示例是按那次做法整理的，不保证逐字一致。这是一套示例配置，不保证按原样跑通；先按自己的引擎和目录调整。

示例用 **完全访问**，因为无头运行没人接审批卡。它不只跳过审批：提供商自己的宽松模式、配置修改，以及某些已连接应用的发送也可能不再问你。团队 brief 里的「不对外发送、不安装软件」是要求，不是技术边界。真正的问题和缺失的凭据仍会等人。改成 ask 后，引擎真的提出只有人才能回答的请求时，`run` 会停止等待并返回退出码 3；第一次输出里会有会话 ID 和开始时间，在 App 里答完卡片后，用 `wait --thread <ID> --since <MS>` 接着等同一条任务。跑通之后，再按下面的建议收紧权限。收紧时三个 Bot 都要检查，已有会话的权限也一起看。在 Bot 设置里选权限时，可以应用到该 Bot 的所有已有会话。总协调的级别会往下传，但只会提高接收方的权限。总协调自己是 ask 时什么都不传，所以把总协调改成 ask 不会把专才降下来。

把这份文件和下面这段一起交给你的 AI Agent。它会补三份 soul、先跑计划、再创建。模型填引擎真实提供的，写法是「实例/模型」。实例名只按第一个斜杠切开，模型名自己带斜杠也没关系。

```text title="交给 AI Agent"
在工作区里用我给你的 team 文件建一支三人小队：总协调 "Alder"、研究员 "Sorrel"、编辑 "Larch"。只允许新增，不要改动或删除任何现有 Bot。

先跑 `openmausbot models`，列出引擎和模型；能不能真正运行，以最后那条测试为准。

然后做三件事：
1. 运行 `openmausbot team export --out backup.yaml`，导出当前的 team 配置：引擎密钥以占位符导出，Custom 审批会跳过。这不是完整备份，导出文件仍要检查并保管；工作区里还没有 Bot 时，跳过这一步。
2. 确认 <shared folder>、<research folder>、<edit folder> 三个目录存在，路径写进 team 文件。
3. 按分工补三份 soul 文件，每份不超过 30 行，必须包含「不负责什么」和交接物的固定格式。

soul 的写法：
- 总协调：拆解、派活、验收、汇总，是唯一对我说话的人；汇报不超过六行。
- 研究员：只产出「要点 | 依据 | 可信度」三列要点表，不写成品，不查无关信息。
- 编辑：只按要点表成稿，不新增事实，写完后回复完整路径、字数和一行来源。

接着：
1. 先跑 `openmausbot team apply <team file> --dry-run`，把计划给我看。
2. 我确认后再跑 `openmausbot team apply <team file>`。
3. 立刻再跑一次，输出应该是 `No changes.`。
4. 用 `openmausbot run "Alder" "用一句话说明你的角色" --timeout 10m` 确认总协调能回一句话；跑不动就停下来告诉我卡在哪一步。

约束：
- 不要在对话、文件或日志里打印任何密钥。
- 改配置前先备份；要改 DNS、路由或时区，先问我。
- 引擎没登录、余额不足、模型不存在时，停下来告诉我，不要自己换模型硬试。
```

## 让它跑一单

三个 Bot 建好后，给总协调一个需要三个岗位的活。文件名、字数、流程都写清楚，它才知道怎么拆。

```text title="发给 Bot 的需求"
为 Demo Lab 写一份《小队运行手册》，文件名 roles.md，放到 <shared folder>，正文 400 到 600 字。

流程：先让研究员给出三个角色的边界要点表，写清各自负责什么、不负责什么、交接物是什么；拿到要点表后再交给编辑成稿并写入文件。

最后由你检查文件是否存在、内容是否齐全，然后只回复我六行以内的总结。
```

从命令行跑这条需求时，给 `run` 带上 `--export <output folder>`，`<output folder>` 用一个新的空目录。导出的是这一条接力任务，下面验证要看的 `job.json` 就在里面。

这段需求里有三个约束。先要要点表，编辑才能动笔。文件名和路径写死，验收才有标准。回复限六行，你才不用读一整页。

## 需要你亲自做的

<Steps>

1. 选一个真的能跑的引擎。换一个模型，或者按引擎自己的方式重新登录，直到一个 Bot 能回一句话。装上 CLI 不等于能用，登录状态要单独确认。

2. 建好三个目录，确认它们的路径。team 文件里的 `cwd` 必须是服务器上已经存在的完整路径，`~` 会被拒绝。

3. 看一遍 dry-run 的计划。计划里应该只有新增，没有 update 或 delete。名字撞上现有 Bot 时，team apply 会按名字合并，这一步能提前发现。

</Steps>

## 几个关键决定

| 决定 | 建议 | 原因 |
|---|---|---|
| 要不要总协调 | 超过两个 Bot 就要 | 只留一个出口，你不会同时收到三份汇报 |
| 权限给到哪一档 | 无头跑用 full，有人盯着时用 ask | 遇到只有人才能回答的请求时，run 默认停止等待并返回退出码 3。ask 下审批也会来问你 |
| 三个 Bot 用同一个模型吗 | 总协调用强的，专才用便宜的 | 判断和验收要质量，列要点和成稿可以省钱 |
| 要不要建群组聊天 | 先不建，需要时再加 | 三个岗位靠私聊委派就够，少一个地方同步 |
| 目录怎么分 | 一个共享目录，两个专才各自一个 | 共享目录是交付区，专才目录是草稿区 |

## 验证

按顺序看三个检查点。

1. 创建成功后如果文件和服务端配置都没变，再跑一次 team apply 会输出 `No changes.`。这说明文件里写的这几项配置已经都在，没有需要再创建的。
2. 打开 `<output folder>/job.json`，三个角色对应的节点都是 `completed`。再确认 `roles.md` 确实在共享目录里。这是接力完成的主要证据。它只证明节点状态和文件存在，内容是否合格还要自己读。
3. 想看过程，打开 `<output folder>/transcripts/` 里总协调那段对话，或者在 App 里打开同一条对话。如果导出完整，会看到给研究员和编辑的委派与回复。导出可能跳过对话或截断消息。单条长消息也可能被截短，清单不一定标出。先看清单，再看原文。具体文字随界面语言变化，不要把某一句固定措辞当成唯一标准。

## 常见问题

**没登录。** 有一次运行里，Claude 的回复是 `Not logged in · Please run /login`。按 Claude 的方式重新登录，或者换一个已经登录的引擎。available 不等于能用。

**余额用完。** 有一次运行里，OpenCode Zen 的回复是 `Your ... balance has run out`，别的引擎措辞可能不同。按量计费的引擎余额用完了。换一个模型，或者给账户充值。

**路径不对。** 写成 `~` 时报错包含 `cwd must be a full path (~ is not expanded the same way on the server)`，写成相对路径时报错包含 `cwd must be an absolute path on the server`。改成服务器上的完整路径。

**模型格式不对。** 报错是 `must be INSTANCE/MODEL, such as claude/claude-sonnet-5-5`。模型要写成「实例/模型」。实例名只取第一个斜杠之前的部分，模型名里带斜杠不用转义。

**再跑一次 team apply，却把你改过的字段改回去了。** team 文件里没写的字段会保持原样，写了的字段会覆盖。要么把文件当成唯一来源，要么别在界面里改同一个字段。

**两个 Bot 抢同一个目录。** 同一时间只让一个 Bot 写共享目录，避免两个进程同时改一份文件。

## 改成适合你的

- 只想要两个 Bot：去掉编辑，让研究员直接交出要点表，总协调自己成稿。
- 想每天自动跑：把这条需求改成例行任务，输出只写在共享目录，并把「没有新内容就不发言」写进指令。
- 想接更多活：加第三个专才时，先给它一个独立目录和一个明确的交接物，再让它进群聊。
